# Phase 2 Feature Report

## Purpose

Phase 2's job was not to build predictive features that make money — it was to turn Phase
1's validated historical data into a reproducible, leakage-safe set of PREGAME football
features. This document is the human-readable record of what was actually built, tested,
audited, and generated, and — as explicitly required — it does **not** report betting
performance, ATS records, ROI, or any outcome-based feature ranking. That belongs to
Phase 4 (backtesting) and beyond.

114 registered entries (104 + 10) is slightly above the "~50-100" initial target. This was
a deliberate, disciplined choice, not scope creep: 56 of the 104 predictive features are
systematic 4-window expansions (3g/5g/8g/season-to-date) of just 14 core efficiency

choice, and asked that correlated window variants not be removed for being correlated. The
underlying number of *distinct football concepts* covered is much closer to 50.

No duplicate-name generation is possible (`scripts/generate_feature_registry.py` asserts
uniqueness), and an exact-equality audit across 108 numeric columns over 7 real seasons
found **zero** columns with identical values under different names — see "Duplicate/alias
audit," below.

## Duplicate/alias audit

Per the continuation instructions, before finalizing the registry, every pair among the
104 predictive numeric columns was checked for exact value-for-value equality across a real
7-season build (2018–2024, 3,884 team-game rows). **Zero exact duplicates found.** No
feature was removed or consolidated as a result — none was needed. Correlated-but-distinct
window variants (e.g. `off_epa_pp_3g` vs. `off_epa_pp_5g`) were deliberately kept, per the
explicit instruction not to remove legitimate correlated variants.

## ALL-PLAY vs. COMPETITIVE-PLAY

See `docs/FEATURE_DICTIONARY.md#all-play-vs-competitive-play` for the full explanation.
Summary: 16 of the 56 windowed columns (the two core overall-efficiency metrics,
`off_epa_pp` and `off_success_rate`, times 4 windows) have a COMPETITIVE-PLAY variant
(`_comp`) that excludes plays where the pre-play home win probability was outside
`[garbage_time_wp_threshold, 1 - garbage_time_wp_threshold]` (`config/feature_engine.yaml`;
`0.05` as of this writing). The filter uses **pre-play** win probability only — never
post-play, never the final score — which is what keeps it leakage-safe. `qb_kneel`/
`qb_spike` plays are excluded from both variants, not for garbage-time reasons, but because
this engine's offensive-play filter (`play_type` in `pass`/`run`) simply never includes
clock-management plays in either view.

## Explosive-play definitions

nflverse provides no canonical "explosive play" flag, so this project defines and
documents its own, conventional thresholds (`config/feature_engine.yaml`):

- **Explosive pass**: a completed pass attempt (`pass_attempt == 1 & complete_pass == 1`)
  gaining **20+ yards** (`yards_gained`).
- **Explosive rush**: a designed rush attempt (`rush_attempt == 1 & qb_scramble == 0`)
  gaining **10+ yards**.

Both thresholds are config values, not hardcoded, and both are applied identically for
offense and the defensive "allowed" counterparts.

## Offensive features: the scramble/rushing boundary

A real design decision, not an accident: **QB scrambles are booked to the passing/QB side,
never the rushing side.** In nflverse's schema, a scramble has `qb_dropback == 1` AND
`rush_attempt == 1` simultaneously (confirmed empirically against real 2024 data — 1,211
scrambles, all double-flagged), so a naive `rush_attempt == 1` filter would silently mix
designed run-game performance with QB improvisation. Every rushing feature in this project
filters `rush_attempt == 1 & qb_scramble == 0` specifically to avoid that. Scramble
contribution is instead captured explicitly under quarterback features
(`qb_scramble_epa_season`).

## QB features and the leakage rule

**This is the highest-risk area of Phase 2 and was specifically re-reviewed per the
continuation instructions (item 10).**

The rule: a game's QB features describe the quarterback identified as **primary in the
team's previous completed game** — never this game's own starter, and never derived from
depth-chart "expected starter" data. Concretely:

1. A play's QB is `passer_player_id` when present (pass attempts and sacks), else
   `rusher_player_id` when `qb_scramble == 1` (a scramble has no `passer_player_id`).
2. For each **completed** game, the "primary QB" is whoever had the most dropbacks for
   that team in that game — computed from that game's own, fully-settled play-by-play.
   This is safe to compute for any game strictly before the one being featured.
3. For target game G, `qb_primary_id` = the primary QB of the team's most recent
   **prior** game — never of G itself.
4. Every `qb_*_season` performance feature (EPA/dropback, success rate, sack rate, INT
   rate, CPOE, scramble EPA) is computed **only from that specific QB's own games** as
   primary QB for this team, this season — not the team's aggregate (which would include
   a backup's snaps), and never his performance in game G.

**Depth-chart-based "expected starter" identification was investigated and explicitly not
used.** Phase 1 already proved (`docs/PHASE1_DATA_REPORT.md`) that the 2025 `depth_charts`
snapshot is a structurally different, unusable data product compared to 2010–2024's
archive format, and there is no evidence that any season's depth-chart snapshot reflects
genuinely pregame-available information rather than a post-hoc record. Rather than build a
leakier "expected starter" feature on unproven ground, Phase 2 keeps QB features scoped to
prior *observed* usage/continuity only, as instructed, and documents this as the limit of
what Phase 2 can safely claim.

**Automated proof** (`tests/features/test_qb_leakage.py`, `tests/features/test_leakage.py`):
a synthetic mid-game QB change (QB_X plays most of game 1, gets hurt in game 2, QB_Y takes
over and plays most of game 2's snaps, then starts game 3) proves:
- Game 2's `qb_primary_id` is QB_X (game 1's primary) — **not** QB_Y, even though QB_Y
  played more of game 2 itself. This is the crux of the rule: game 2's pregame feature
  cannot know a change would happen mid-game.
- Game 3's `qb_primary_id` correctly becomes QB_Y, one game after the change actually
  happened, using only fully-completed information.
- Mutating game 3 arbitrarily (a different QB, wildly different stats) leaves games 1 and
  2's QB features completely unchanged.

**Verified against a real 2024 case** (see "Manual audit," below): Cleveland's primary
passer changed between weeks 6 and 7 of 2024 (GSIS `00-0033537` → `00-0038583`). Week 8's
`qb_primary_id` correctly shows `00-0038583` with `qb_starts_season = 1`, and
`qb_epa_dropback_season` (`-0.7727358986646868`) was independently recomputed from that
QB's own 25 dropbacks in week 7 alone and matches the engine's output to full floating-point
precision.

**Known limitation, documented rather than hidden**: "primary QB" means whoever had the
most dropbacks in a game, not necessarily the officially designated starter — in the rare
case a starter is pulled after one series and a backup plays the rest, "primary" correctly
tracks the backup. This is the right behavior for a performance-context feature (it's about
who the team's passing production will most resemble), but it is not identical to a
box-score "starter" field.

## Opponent context

Deliberately a simple average, not a learned strength-of-schedule model, per the explicit
instruction to defer a "too model-like" opponent adjustment to Phase 3.
`opp_off_epa_faced_season`/`opp_def_epa_faced_season` average each opponent's own pregame
season-to-date rating **at the time of that specific meeting** across all of a team's
meetings so far this season. Because each opponent's rating is itself already leakage-safe
(it never includes games after that meeting), averaging already-safe values introduces no
new leakage — but there is no recursive convergence, no sample-size weighting of the
opponents' own ratings, and no adjustment for how many games each opponent's rating was
based on. These are real limitations, left for Phase 3 to address if warranted, not silently
smoothed over.

## Personnel continuity

`off_snap_continuity_pct`/`def_snap_continuity_pct` (2013+, when `snap_counts` coverage
begins) compare a team's most recent two completed games to each other — never the target
game's own roster. This is self-referential within `snap_counts` specifically because that
dataset identifies players by `pfr_player_id` (Pro-Football-Reference), a different
namespace than play-by-play's GSIS ids; reconciling the two would need a player-ID
crosswalk this project hasn't built, so continuity was designed to avoid needing one at
all. Like the trailing-game-count windows, this does **not** reset at season boundaries —
Week 1 of a new season compares the prior season's last two games, which is why coverage
reaches 100% starting in the *second* season after `snap_counts` begins (2014), not
immediately in 2013.

## Turnovers

Deliberately split into process-style rates (`off_int_rate`, `off_fumble_lost_rate`,
`def_int_rate_generated`, `def_fumble_forced_rate`) rather than one combined
"turnover margin" figure, and explicitly not presented as a stable predictive measure —
interceptions and fumbles are genuinely noisy outcomes, and this project makes no claim
that they repeat perfectly game to game.

## Special teams

Deliberately restrained, per the brief. `fg_pct_season` and `punt_yards_avg_season` only.
Punt yardage is **gross**, not net — computing true net punting would require reconciling
touchbacks, fair catches, out-of-bounds spots, and return yardage, which this project isn't
leaning on yet. Return performance is deferred entirely.

## Small-sample situational statistics

Third-down conversion rate and red-zone touchdown rate are provided (offense and defense),
but every registry entry for them explicitly cautions against treating them as inherently
stable: a team may see only 10–15 third-down attempts or 2–5 red-zone trips in a single
game, so early-season samples are genuinely small. `redzone_trips_n`/`redzone_trips_n_allowed`
are exposed specifically so a downstream consumer can see this.

## Rolling windows and sample size

Two kinds (full explanation in `docs/FEATURE_DICTIONARY.md#rolling-windows`):
**trailing N games** (3/5/8; does not reset at season boundaries) and **season-to-date**
(resets every season). **Previous-season** features are a third, distinct thing: a full
prior-season total, held constant across the following season — deliberately *not* the same
number as that prior season's own final `_season` value (which excludes that season's last
game, following the same "strictly before" rule as everything else).

Sample-size context is exposed via 10 shared counters
(`games_played_current_season`, `n_games_trailing_3/5/8`, `qb_starts_season`,
`redzone_trips_n(_allowed)`, `fg_attempt_n`, `punt_n`, `has_prev_season_data`) rather than
one counter per metric, because every metric computed over the same window draws on the
identical set of prior games. This was a deliberate design trade-off to stay within the
target feature-count budget while still satisfying "so later models know the sample size."

**Documented, not-a-bug characteristic discovered during the manual audit**: rolling and
season-to-date windows are **not** filtered by `season_type` — a completed postseason game
counts as a real prior game once it happens (confirmed: Philadelphia's `prev_season_off_epa_pp`
for 2024, `0.043762...`, independently recomputed from the full 2023 season including their
Week 19 playoff loss, matched the engine exactly). This is defensible (a playoff game is a
real, completed game with real signal) but worth flagging: playoff-game samples are smaller
and against playoff-caliber opponents specifically, a subtlety Phase 3 should be aware of
if it ever needs to reason about why an early-2024 rolling window looks slightly different
from a pure-regular-season expectation.

## Missing data policy

No feature is ever silently filled with zero unless zero is the semantically correct value
(e.g. `games_played_current_season = 0` in Week 1 is a real zero, not a missing value).
Every rate/EPA feature is `null` — not `0` — until its minimum observation count is met.
Verified directly: every Week 1 2024 row has `off_epa_pp_season = null`,
`off_redzone_td_rate_season = null`, and `qb_epa_dropback_season = null`
(`tests/features/test_quality.py::test_week_1_behavior_is_valid`,
`test_nulls_follow_documented_policy_never_silently_zero`).

## Manual football audit

Six real games, selected to cover every required scenario, with several feature values
manually traced back to the exact prior games that produced them and independently
recomputed from raw play-by-play — not merely eyeballed for plausibility.

### 1. Week 1 — Philadelphia (team `3700`), `2024_01_GB_PHI`

- `games_played_current_season = 0`, `days_rest = null`, `off_epa_pp_season = null` (correct
  — no games this season yet).
- `off_epa_pp_3g = -0.10042386601967569`. Trailing window uses `2023_17_ARI_PHI` (47 plays),
  `2023_18_PHI_NYG` (65 plays), `2023_19_PHI_TB` (54 plays) — the team's last 3 games,
  spanning the END of the PRIOR season (166 total plays), confirming the trailing window
  correctly does not reset at the season boundary. Independently recomputed directly from
  `data/normalized/play_by_play/season=2023/data.parquet` (summing `epa` for
  `posteam_id == '3700'` on `play_type in (pass, run)` across those 3 `game_id`s, divided by
  166 plays): **-0.10042386601967565** — matches to 13 significant figures (the tiny residual
  is floating-point summation-order noise, not a discrepancy).
- `prev_season_off_epa_pp = 0.04376249848058371`. Independently recomputed from the FULL 2023
  season (18 games including the Week 19 playoff loss, 1,158 plays): **0.04376249848058371**
  — exact match.
- `qb_primary_id = null`, `qb_consecutive_starts = 0` — correct: no prior game exists to
  identify a primary QB from.

### 2. Early season — Philadelphia, `2024_02_ATL_PHI` (Week 2)

- `games_played_current_season = 1`, `days_rest = 10`, `opponent_days_rest = 8`.
- `qb_primary_id = 00-0036389`, `qb_starts_season = 1`,
  `qb_epa_dropback_season = 0.3723639727931617` — describes the Week 1 game's primary QB,

- `off_pass_epa_dropback_season = 0.3723639727931617` — team-level and QB-level values

### 3. Late season — Philadelphia, `2024_14_CAR_PHI` (Week 14)

- `games_played_current_season = 12`, `days_rest = 6` (a short week), `qb_consecutive_starts
  = 12` (the same QB, `00-0036389`, has started every game so far).
- `off_epa_pp_3g = 0.20671109387810682`, drawing on weeks 11, 12, 13
  (`2024_11_WAS_PHI`, `2024_12_PHI_LA`, `2024_13_PHI_BAL`) — confirmed via the same
  chronological-index reconstruction used in test C.
- `qb_epa_dropback_season = 0.1489111218420787` vs. team-level
  `off_pass_epa_dropback_season = 0.13920469501612565` — now visibly different from each
  other (unlike the Week 2 case), because the team aggregate blends in whatever backup
  snaps occurred across the season while the QB-specific figure stays scoped to `00-0036389`'s
  own 12 starts.

### 4. Bye-week return — Chicago (team `0810`), `2024_08_CHI_WAS` (Week 8)

- `days_rest = 14`, `post_bye = True`, `opponent_days_rest = 7` (Washington did not have a
  bye) — `rest_diff = 7`.
- `games_played_current_season = 6` at Week 8 — one fewer than the `week - 1 = 7` a team
  without a bye would show, correctly reflecting the missed week.
- `off_epa_pp_3g` draws on `2024_04_LA_CHI`, `2024_05_CAR_CHI`, `2024_06_JAX_CHI` — the three
  games before the bye (there being no Week 7 game to include), confirming the trailing
  window correctly skips over the bye week rather than fabricating a phantom game or
  shrinking the window's game *count* (it's still exactly 3 games, just spread across more
  calendar time).

### 5. QB continuity/change — Cleveland (team `1050`), `2024_08_BAL_CLE` (Week 8)

Independently confirmed (not merely read from the engine): Cleveland's primary passer was
`00-0033537` in weeks 5–6, then `00-0038583` became primary in week 7
(`2024_07_CIN_CLE`, 25 of his own dropbacks that game). Week 8's row correctly shows:
- `qb_primary_id = 00-0038583`, `qb_starts_season = 1`, `qb_consecutive_starts = 1`.
- `qb_epa_dropback_season = -0.7727358986646868` — recomputed directly from `00-0038583`'s
  own 25 dropbacks in week 7 (`sum(epa) = -19.31839746661717`, `-19.31839746661717 / 25 =
  -0.7727358986646868`): **exact match**.
- `off_pass_epa_dropback_season = -0.217574723389859` (team aggregate, blending both QBs'
  snaps across weeks 1–7) is visibly different from the QB-specific value — direct evidence
  the two are genuinely independent computations, not one masquerading as the other.

### 6. Mismatched prior-games-played — Pittsburgh (team `3900`) vs. Baltimore, `2024_11_BAL_PIT` (Week 11)

- Home (Pittsburgh): `games_played_current_season = 9`. Away (Baltimore):
  `games_played_current_season = 10` — a real one-game gap between the two teams heading
  into the same Week 11 kickoff (bye weeks land on different weeks for different teams).
- Confirms `games_played_current_season` is computed strictly per-team from that team's own
  schedule, never assumed equal to `week - 1` for both sides of a game.

## Known limitations

- Third-down and red-zone rates can be small-sample early in a season (see "Small-sample
  situational statistics," above).
- Personnel continuity is offense/defense-wide, not position-specific (e.g. no
  offensive-line-only continuity) — deferred, since reliable position mapping onto
  `snap_counts` wasn't established this phase.
- Opponent-quality context is a simple average, not a rigorous strength-of-schedule model
  (see "Opponent context," above).
- Punt yardage is gross, not net; return performance is not modeled at all.
- "Primary QB" is usage-based (most dropbacks in a game), not an official starter
  designation — see "QB features and the leakage rule."
- Rolling/season-to-date windows include postseason games without distinction from regular
  season (see "Rolling windows and sample size").
- No weather, travel distance, altitude, or timezone-change features — Phase 1 data doesn't
  reliably support them yet, per the original brief's instruction not to add them without
  dedicated source data.
- CPOE features use play-by-play's own model, not the separate nflverse Next Gen Stats
  dataset — see "Season coverage and historical availability."

## Features intentionally deferred (not built in Phase 2)

- True pressure rate, pass-block win rate, pass-rush win rate (nflverse doesn't reliably
  provide these; proxies — sack rate, QB-hit rate — were used instead and documented as
  proxies).
- Offensive-line-specific or position-specific snap continuity.
- Net punting, punt/kickoff return performance.
- A learned/recursive opponent-strength-adjustment model.
- Any feature derived from Next Gen Stats (`nextgen_passing`/`receiving`/`rushing`),
  depth charts, or historical betting-market fields (the latter deliberately, permanently,
  per `docs/PHASE1_DATA_REPORT.md#football-data-vs-market-data`).
- Weather, travel, altitude, timezone-change context.
- Any feature selection, weighting, or evaluation based on game outcomes, ATS results, or
  betting performance — that is explicitly out of scope for Phase 2 and belongs to Phase 4+.
